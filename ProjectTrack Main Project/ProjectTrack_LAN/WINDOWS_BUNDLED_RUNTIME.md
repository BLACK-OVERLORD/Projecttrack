# Windows Bundled-Runtime Packaging

## Goal

The packaged Windows edition uses `jpackage` to create two self-contained app-images:

```text
release/
├── ProjectTrack Client/
│   ├── ProjectTrack Client.exe
│   ├── app/
│   │   └── ProjectTrackClient.jar
│   └── runtime/
│       └── ... bundled Java runtime ...
│
└── ProjectTrack Server/
    ├── ProjectTrack Server.exe
    ├── app/
    │   └── ProjectTrackServer.jar
    ├── runtime/
    │   └── ... bundled Java runtime ...
    └── data/
        └── ...
```

The Windows client therefore does **not** need Java installed.

## Build requirements for the packaging computer

The packaging computer must be Windows and must have JDK 21 or newer installed. The JDK must provide `jpackage`.

Check:

```cmd
java -version
jpackage --version
```

The target client/server PCs do not need Java after the app-images have been created.

## Build

1. Run `build.bat`.
2. Run `package_windows.bat`.
3. Run `verify_windows_packages.bat`.

The EXEs will be:

```text
release\ProjectTrack Client\ProjectTrack Client.exe
release\ProjectTrack Server\ProjectTrack Server.exe
```

Each app-image contains its own `runtime` folder generated by `jpackage`.

## Distribution

For the server PC, copy the complete:

```text
release\ProjectTrack Server\
```

folder.

For each client PC, copy the complete:

```text
release\ProjectTrack Client\
```

folder.

Do not copy only the EXE. The `runtime` folder and application files are part of the self-contained package.

## Important limitation of this development environment

The current development environment used to prepare this ZIP is Linux, so Windows `jpackage` output cannot be executed or validated here. The project includes the Windows packaging scripts and all configuration needed to create the actual Windows EXEs on a Windows machine.

`jpackage` is used specifically because it creates native Windows application images with a bundled Java runtime, while Launch4j is also capable of producing Windows native EXE wrappers and bundling a JRE. The ZIP uses the JDK-provided `jpackage` path for the final packaging workflow.
